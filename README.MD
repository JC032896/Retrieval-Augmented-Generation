# 권한 인식 한국어 문서 질의 서비스 (RAG)

> 사내 문서를 올리면, **질문한 사람이 볼 수 있는 문서 안에서만** 근거를 찾아 **출처와 함께** 답하는 서비스.
> 근거가 없으면 지어내지 않고 **"문서에서 찾을 수 없습니다"**라고 답한다.
> 모든 개선은 **평가 지표로 증명**한다.

---

## 1. 해결하려는 문제

| 실무 문제 | 이 프로젝트의 해결 방법 |
|---|---|
| 벡터 검색은 "제12조의3", "KPI-2024-A" 같은 코드나 약어를 놓치고, 키워드 검색은 한국어 조사 때문에 망가진다 | **Kiwi 형태소 BM25, 벡터 검색, RRF 결합, 리랭커를 모두 구현해 평가로 비교하고, 가장 좋은 조합(벡터 + 리랭커)을 기본으로 사용** |
| AI가 근거 없이 그럴듯하게 지어낸다 (환각) | **근거 부족 시 답변 거절 + 문장 단위 인용 검증** |
| 인사, 재무 문서가 권한 없는 직원의 답변에 섞여 나온다 | **회사 로그인으로 사용자를 확인하고, 권한 정보를 조각마다 저장해 검색 SQL 단계에서 미리 필터링** |
| 뭘 바꿔도 좋아졌는지 알 수 없다 | **골든 데이터셋 + 자동 평가 + CI 품질 게이트** |

## 2. 핵심 기능

### B. 한국어 검색 + 리랭커
- **키워드 검색**: Kiwi(kiwipiepy)로 형태소를 분석한 토큰을 Postgres 전문 검색(`tsvector`, `simple` 설정)에 저장한다.
- **의미 검색**: 다국어 임베딩 모델 BGE-M3로 만든 벡터를 pgvector에 저장한다.
- **결합**: 두 결과를 RRF(Reciprocal Rank Fusion)로 합칠 수 있다.
- **재정렬**: 후보 20개를 크로스 인코더 리랭커(bge-reranker-v2-m3)로 다시 정렬해서 상위 5개를 고른다.
- **기본 검색기는 "벡터 상위 20 + 리랭커"다.** 이 데이터에서는 BM25를 섞으면 오히려 나빠졌다
  (6절). 검색기는 설정으로 바꿀 수 있고, 데이터가 바뀌면 같은 평가로 다시 고른다.

### G. 답변 거절과 인용
- 검색된 조각에 번호를 붙여 LLM에 전달하고, 답변에 `[1]`, `[2]` 형식으로 인용하게 한다.
- 거절은 2단이다. 검색 결과가 없으면 LLM을 호출하지 않고 **거절**하고, 결과가 있으면 LLM이 근거를
  읽고 답이 없으면 거절 문구로 답한다. 리랭커 점수 기준값으로 거절하는 관문도 있지만, 측정해 보니
  정답까지 거절해서 기본으로 꺼 두었다 (6절 "거절 기준").
- 답변의 각 문장이 인용한 조각에 실제로 근거하는지 **사후 검증**한다.
- 출처는 문서명, 페이지, 섹션 단위로 표시한다.

### E. 권한 기반 검색
- 문서마다 열람 가능한 **부서와 역할**, **보안 등급**을 지정하고, 이 정보를 모든 조각에 복사해 저장한다.
- 검색 쿼리의 `WHERE` 절에서 **검색 전에** 걸러낸다. 검색한 뒤에 걸러내는 방식은 쓰지 않는다.
- 질문한 사용자는 회사 로그인 시스템의 토큰(OIDC)으로 확인하고, 부서·역할·등급은 서버 DB에서 읽는다.
  요청에 실려 온 권한 값은 믿지 않는다 (6절 "질문 API").
- 지금은 권한만 바뀌어도 문서를 다시 수집한다(임베딩 재계산). 권한 사본만 갱신하는 기능은 계획이다
  (7단계 증분 수집).
- **권한 없는 조각이 결과에 섞이는 건수 = 0**을 테스트로 보장한다.

### A. 평가와 회귀 테스트
- **골든 데이터셋** (`eval/golden.jsonl`, 버전 관리)

  | 유형 | 목적 | 개수 |
  |---|---|---|
  | 일반 질문 | 검색 정확도와 답변 품질 측정 | 40 |
  | 정확한 코드·약어 질문 | 하이브리드 검색 효과 측정 (비슷한 코드 체계와 혼동하는지 포함) | 15 |
  | 표현을 바꾼 질문 (paraphrase) | 문서와 다른 단어로 물어도 찾는지 측정 ("재택" 대신 "집에서 일하기") | 20 |
  | 문서에 답이 없는 질문 | 거절 정확도 측정 | 10 |
  | 권한 함정 질문 (권한 없는 사용자로 질문) | 정보 유출 여부 검증 | 10 |

- **헷갈리는 문서**: 샘플 22개 중 7개는 정답 문서와 비슷하지만 틀린 문서다 (폐지된 구버전 규정,
  비슷한 코드 체계를 쓰는 다른 제품 문서 등). 실제 사내 문서처럼 검색이 쉽게 맞히지 못하게 한다.
  그중 폐지된 구버전 3개는 `acl.yaml`에 `status: superseded`로 표시되어 기본 검색에서 빠진다.

- **지표**

  | 구분 | 지표 |
  |---|---|
  | 검색 | Recall@5, MRR |
  | 답변 | 인용 적중(정답 문서를 인용했는가), 인용 정밀도, 인용 검증 통과율(규칙 기반 근거 대조) |
  | 거절 | 거절 정밀도와 재현율 (답 없는 질문은 거절하고, 답 있는 질문은 거절하지 않는가) |
  | 보안 | 권한 유출 건수 (반드시 0) |
  | 운영 | 질의당 토큰과 비용 |

  LLM이 답의 정확성을 채점하는 지표와 응답 시간(P95) 측정은 아직 없다 (계획).

- **CI 게이트**: 코드를 바꿀 때마다 평가를 실행하고, 기준선보다 떨어지거나 권한 유출이 1건이라도 생기면 실패 처리한다.

## 3. 아키텍처

```
[UI (계획)] ──HTTP/SSE──▶ [FastAPI] ◀── 회사 로그인(OIDC) 토큰 검증
                              │
         ┌────────────────────┼─────────────────────┐
         ▼                    ▼                     ▼
  [수집 파이프라인]      [검색 파이프라인]        [답변 생성]
  파싱 → 청킹 →          사용자 권한 필터        번호 붙인 근거로 프롬프트 구성
  Kiwi 토큰화 +          → 벡터 검색 (BM25·RRF   → LLM 스트리밍 답변
  임베딩 → 저장             는 선택) → 리랭커     → 인용 검증
         │                    │                  → 근거 부족 시 거절
         ▼                    ▼
   [PostgreSQL + pgvector]  documents / document_acl / chunks / users
```

## 4. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | FastAPI (Python) | AI와 검색 생태계가 Python 중심 |
| DB | PostgreSQL + pgvector | 벡터, 키워드, 권한 필터를 **한 번의 SQL**로 처리 |
| 한국어 형태소 분석 | Kiwi (kiwipiepy) | 조사를 분리해서 한국어 키워드 검색 품질 확보 |
| 임베딩 / 리랭커 | BGE-M3 / bge-reranker-v2-m3 | 한국어를 지원하고 로컬에서 실행 가능 |
| LLM | Claude API (기본 Sonnet 5.5) | 출처 인용과 지시 준수. 모델 비교는 6절 |
| 인증 | OIDC (PyJWT) | 회사가 쓰는 로그인 시스템(Microsoft 365, Google 등)을 그대로 사용 |
| 평가 | 직접 작성한 스크립트 | 규칙 기반 지표라 API 없이 CI에서 같은 결과가 나온다 |
| 작업 큐 (후순위) | Celery + Redis | 대용량 문서 비동기 처리 |
| 프론트엔드 (후순위) | Next.js | 최소한의 채팅, 출처, 업로드 화면 |
| 실행 환경 | Docker Compose | 명령 한 줄로 실행 |

## 6. 실험 결과

> 구현하면서 채운다. 검색 지표는 `uv run python eval/run_eval.py --compare`로 다시 만들 수 있다.
> 골든 v2(답이 있는 질문 75개), 샘플 22개(헷갈리는 문서 7개 포함), 정확한 전체 비교(flat) 기준.

**현재 (폐지 문서 3개를 검색에서 제외)**

| 구성 | Recall@5 | MRR | Hit@1 | Hit@1 (표현 바꾼 질문) | 권한 유출 |
|---|---|---|---|---|---|
| 벡터만 (BGE-M3) | 1.000 | 0.973 | 0.947 | 0.950 | 0 |
| Kiwi BM25만 | 0.893 | 0.808 | 0.747 | 0.300 | 0 |
| 벡터 + BM25 (RRF 1:1) | 0.973 | 0.892 | 0.827 | 0.450 | 0 |
| **벡터 상위 20 + 리랭커** (기본) | **1.000** | **0.980** | **0.960** | 0.950 | 0 |
| (벡터 20 ∪ BM25 20) + 리랭커 | 1.000 | 0.980 | 0.960 | 0.950 | 0 |

**벡터 + BM25 결합이 벡터 단독보다 나빴다.** BGE-M3가 한국어 의미와 코드(`SEC-PW-01` 등)를 이미 잘
잡아서, BM25가 더하는 신호보다 잡음이 컸다. BM25는 문서와 다른 단어로 물으면 거의 찾지 못했고
(표현 바꾼 질문 Hit@1 0.25), 비슷한 코드 체계를 쓰는 헷갈리는 문서(`SEC-PW-04`)에 단어가 많이 겹쳐
코드 질문에서도 벡터보다 낫지 않았다. 벡터를 2배로 가중해도 MRR 0.892로 벡터 단독(0.927)에 못
미쳤다. 75문항에 가중치를 맞추면 과적합 위험이 있어 조정하지 않았다. 기본 검색기는 벡터로 두고,
리랭커 단계에서 "벡터 상위 20개"와 "벡터 + BM25 합집합"을 후보로 넣어 다시 비교한다.

**리랭커(bge-reranker-v2-m3)는 작게 개선했다** (MRR 0.927 → 0.940, Hit@1 0.853 → 0.880).
6문항을 고치고 4문항을 새로 틀려 순효과는 2문항이다. 조항 번호 혼동(제12조의2)과 구버전 영업
가이드는 고쳤지만, **폐지된 구버전 문서가 1위가 되는 문제는 리랭커로 풀리지 않았다**. 리랭커는
"질문과 관련 있는가"만 보므로 2025년판 출장비 규정도 현행 규정만큼 관련 있다고 판단한다 (0.97점).
남은 오답 9개 중 5개가 이 경우라서, 검색 알고리즘이 아니라 문서 수명(현행/폐지) 메타데이터로 다룬다.
BM25로 후보를 넓혀도 결과가 같아서, 더 싼 "벡터 상위 20 + 리랭커"를 기본 검색기로 쓴다.
CPU에서 질문당 약 2.3초(후보 20개)가 든다.

**문서 수명 메타데이터가 가장 크게 개선했다** (기본 검색기 MRR 0.940 → 0.980, Hit@1 0.880 → 0.960).
`acl.yaml`에서 문서마다 `status`(현행 `current` / 폐지 `superseded`)를 지정하고, 검색은 기본으로
현행 문서만 후보로 삼는다 (지난 규정을 찾을 때만 `include_superseded=True`). 상태는 `documents`
한 곳에만 두어서, 새 판이 나오면 한 행만 바꾸면 되고 조각과 임베딩은 그대로 둔다. BM25의 IDF와
평균 길이도 현행 문서만으로 계산한다. 폐지 문서가 1위를 차지하던 5문항이 모두 풀렸고, 벡터 단독도
Hit@1 0.947까지 올라서 리랭커의 몫은 1문항(0.947 → 0.960)으로 줄었다. 남은 오답 3개(c006, g029,
v019)는 정답이 2위 안에 있다.

주의할 점: 이 개선은 검색 알고리즘이 아니라 **문서 관리 정보**에서 나왔다. 실제 서비스에서는 누가
폐지 표시를 하느냐(문서 관리 절차)가 품질을 좌우한다. 또 골든 데이터셋에는 아직 "작년 규정은
어땠나"처럼 폐지 문서를 찾아야 하는 질문이 없어서, `include_superseded=True` 경로는 단위 테스트로만
검증한다.

### 거절 기준 (4단계)

리랭커 1위 점수가 기준값 미만이면 거절하는 방식을 골든 95문항(거절해야 할 질문 20개)으로 측정했다.

| 리랭커 점수 기준값 | 맞게 거절 (20개 중) | 잘못 거절 (답 있는 75개 중) | 거절 F1 |
|---|---|---|---|
| 0.001 | 4 | 1 | 0.32 |
| 0.003 | 10 | 2 | 0.63 |
| 0.01 | 15 | 4 | 0.77 |
| 0.05 | 15 | 9 | 0.68 |

**점수만으로는 거절할 수 없다.** 실패는 양쪽에서 나온다.
- 일상어로 바꾼 질문은 1위가 정답이어도 점수가 0에 가깝다. "바닷가 쪽 숙소를 싸게 쓸 수 있는
  방법이 있어?"는 휴양소 조각을 1위로 찾았지만 0.00038점으로, 95문항 중 두 번째로 낮았다.
  그래서 정답을 하나도 잘못 거절하지 않는 기준값은 사실상 0이다.
- 주제는 같고 답은 없는 질문은 점수가 높다. "인사평가 등급별 배분 비율"(권한 함정)은 취업규칙의
  인사평가 조항이 0.898점, "INC-P5 등급 장애의 대응 기준"(없는 등급)은 장애 대응 매뉴얼이
  0.625점이다. 답이 실제로 들어 있는지는 내용을 읽어야 알 수 있다.

그래서 거절을 2단으로 나눴다. 1단 점수 관문은 기본으로 검색 결과가 없을 때만 거절하고,
2단에서 LLM이 근거를 읽고 답이 없으면 거절한다. 점수 관문은 LLM 판단 결과가 나온 뒤
비용 절감용으로만, 잘못 거절이 생기지 않는 범위에서 켠다.

### 인용 답변과 모델 비교 (4단계)

검색(vector_rerank) 상위 5개 조각에 번호를 붙여 LLM에 주고, 문장마다 `[번호]`로 인용하며 답이 없으면
거절 문구로 시작하게 했다. 골든 95문항을 모델별로 답하게 하고 규칙으로 채점했다
(`run_eval.py --compare-models`, effort medium, 2026-11-09).

| 모델 | 거절해야 할 때 거절 (20개) | 잘못 거절 (75개) | 정답 위치 인용 | 인용 정밀도 | 문항당 비용 |
|---|---|---|---|---|---|
| Haiku 5.5 | 1.000 | 0.040 (3개) | 1.000 | 0.958 | $0.0002 |
| **Sonnet 5.5 (기본)** | 1.000 | 0.000 | 1.000 | 0.902 | $0.0038 |
| Opus 5.5 | 1.000 | 0.000 | 1.000 | 0.886 | $0.0090 |

- 정답 위치 인용: 답한 질문 중 정답 위치(파일, 섹션)를 하나라도 인용한 비율.
  인용 정밀도: 인용한 조각 중 정답 위치인 비율의 평균.
- 점수만으로는 못 거른 질문(권한 함정 0.898점 등)을 세 모델 모두 거절했다. 2단 거절에서 2단이 하는 일이다.
- Haiku의 잘못 거절 3개는 "문서에서 찾을 수 없습니다. 다만 제12조의3에 따르면 …"처럼 거절 문구 뒤에 맞는
  답을 붙인 경우다. 내용은 맞지만 조심이 지나쳐 서비스에서는 거절로 보인다.
- 비싼 모델일수록 근거를 더 많이 인용해 정밀도가 조금 낮다. 답 내용이 정답과 맞는지는 아직 채점하지
  않았다 (인용 검증 뒤에 LLM 채점으로 추가 예정).
- 기본 모델은 잘못 거절이 없는 가장 싼 모델인 Sonnet으로 정했다. 사원 1,000명이 하루 2,500문항을
  물으면 약 $9.5/일이다. Haiku는 20배 싸므로 잘못 거절을 줄이면 후보가 된다.
- 첫 실행에서 Sonnet이 답 없는 질문 1개(u006)를 거절 문구 없이 "문서에는 … 적혀 있지 않습니다"로
  거절해, 거절 문구로 "시작"하라고 프롬프트를 고친 뒤 위 표를 다시 측정했다.

### 인용 검증 (4단계)

답변을 문장으로 나눠 인용한 조각과 규칙으로 대조한다 (`answer/verify.py`, LLM 호출 없음).
숫자와 코드(`INC-P1`, `제12조의3`)는 인용 조각이나 질문에 그대로 있어야 하고, 내용 형태소는 60% 이상
인용 조각에 있어야 한다. 인용 없는 문장은 그 답이 인용한 조각 전체와 대조한다
("네, 가능합니다."처럼 결론을 먼저 말하는 문장이 많다).

검증기 자체를 측정하려고 세 모델의 실제 답변 222개와 일부러 틀리게 고친 답변을 썼다.

| 측정 | 결과 |
|---|---|
| 숫자 하나를 바꾼 답 (7일 → 8일) 검출 | 187 / 216 (87%) |
| 인용 번호를 다른 문서 조각으로 바꾼 답 검출 | 206 / 209 (99%) |
| 실제 답 중 경고가 난 답 | 10 / 222 (4.5%) |

- 처음에는 숫자만 비교해서 74%만 잡았다. "1박"을 "2박"으로 바꿔도 조각에 "2만 원"이 있으면
  통과했기 때문이다. 숫자를 단위와 함께 비교하고 코드를 통째로 비교해 87%가 됐다.
  남은 13%는 바뀐 값(`INC-P2`, 9시)이 같은 조각의 다른 줄에 실제로 있는 경우로, "근거에 있는가"만
  보는 방식으로는 잡을 수 없다.
- 실제 답의 경고 10개 중 Haiku의 2개는 문서에 없는 숫자를 직접 계산한 답이다
  ("15일에서 최대 10일이 늘어날 수 있습니다", "1만 2천 500원"). 계산이 맞더라도 근거가 없으므로
  경고가 맞다. 나머지는 "참고로 알아 두실 점이 있습니다" 같은 군더더기 문장의 오탐이다.
- 기준값(내용 겹침 60%)을 같은 답변으로 골랐으므로 새 문서에서는 다시 확인해야 한다.
  부정("할 수 있다" ↔ "할 수 없다")은 단어가 같아서 잡지 못한다.

| 모델 | 인용 검증 통과 |
|---|---|
| Haiku 5.5 | 0.931 |
| Sonnet 5.5 | 0.973 |
| Opus 5.5 | 0.960 |

CI는 `eval/cache/answers.json`에 저장한 답으로 API 없이 평가한다. 프롬프트나 검색 결과가 바뀌면
캐시 키가 달라져 평가가 실패하므로, `--update-cache`로 답을 다시 받아야 한다 (Sonnet 약 $0.36).

### 질문 API와 SSE 스트리밍 (4단계)

`POST /ask {"question": "..."}`는 답변을 SSE(`text/event-stream`)로 흘려보낸다 (`api/ask.py`).

```
uv run python -m rag_service.ingest samples        # 문서와 사용자(users 테이블)를 수집
AUTH_MODE=dev_header uv run uvicorn rag_service.main:app
curl -N -X POST localhost:8000/ask -H "X-User-Id: kim" -H "Content-Type: application/json" \
     -d '{"question": "출장비 정산은 언제까지 해야 해?"}'
```

| 이벤트 | 내용 |
|---|---|
| `delta` | 답변 조각 `{"text"}`. 이어 붙여 보여 준다 |
| `done` | 마지막 이벤트. 최종 답변, 인용, 인용 검증 결과, 토큰과 비용 |
| `error` | LLM 실패. 이 이벤트로 끝난다 |

- 사용자 확인, 입력 검증, 검색은 스트림을 열기 전에 끝내서 실패하면 일반 HTTP 오류로 돌려준다
  (헤더 없음·미등록 사용자 401, 빈 질문 422, `AUTH_MODE`나 API 키 미설정 503).
- 신원과 권한 속성을 나눴다. 요청에서는 로그인 id만 받고, 부서·역할·보안 등급은 DB `users`
  테이블에서 읽는다 (수집할 때 `org.yaml`과 맞춘다). 요청에 실린 권한 값을 믿지 않으므로 퇴사나
  등급 변경이 다음 요청부터 반영된다.
- LLM이 거절 문구로 시작하면 그 텍스트는 흘려보내지 않고 `done(refused=true)`만 보낸다.
  "문서에서"까지만 왔을 때는 판단이 설 때까지 모아 둔다.
- `AUTH_MODE=dev_header`는 헤더 값을 그대로 믿는 개발·데모 전용이다 (누구나 다른 사람 행세 가능).
  기본값 `disabled`에서는 질문 API가 503을 돌려준다.

#### 회사 로그인 연동 (OIDC)

운영에서는 `AUTH_MODE=oidc`로 회사가 이미 쓰는 로그인 시스템의 토큰을 받는다 (`api/oidc.py`).
OIDC 표준만 구현했으므로 회사마다 코드를 바꾸지 않고 설정만 넣는다.

```
AUTH_MODE=oidc
OIDC_ISSUER=https://login.microsoftonline.com/<테넌트 ID>/v2.0   # Microsoft 365
OIDC_AUDIENCE=<로그인 시스템에 등록한 이 앱의 ID>
OIDC_LOGIN_CLAIM=email                                         # users.login과 맞출 토큰 값
```

| 회사 상황 | 로그인 시스템 |
|---|---|
| Microsoft 365를 쓰는 회사 | Entra ID |
| Google Workspace를 쓰는 회사 | Google |
| 계정 시스템이 없는 회사 | Keycloak(오픈소스)을 함께 띄운다 (배포 단계에서 예시 제공 예정) |
| SAML 방식의 오래된 사내 SSO | Keycloak이 중계한다 (앱은 계속 OIDC만 쓴다) |

- 요청은 `Authorization: Bearer <토큰>`으로 보낸다. 로그인 서버의 공개 키로 서명, 발급자, 대상 앱,
  만료를 확인하고, 공개 키 서명 알고리즘만 허용한다 (`none`이나 HS256으로 위조한 토큰 거부).
- 공개 키는 캐시한다. 모르는 키 id가 오면 키 교체로 보고 다시 받되, 위조 토큰으로 로그인 서버에
  요청이 몰리지 않게 60초에 한 번으로 제한한다.
- 로그인 서버에 연결할 수 없으면 503, 토큰이 잘못됐으면 401(`WWW-Authenticate: Bearer`)이다.
- 메일 주소로 사용자를 찾을 때는 소문자로 바꾸고, 로그인 서버가 확인 안 된 메일이라고 표시한
  토큰은 거부한다. 이때 `users.login`(수집 시 `org.yaml`의 id)도 소문자 메일 주소여야 한다.

### 감사 기록과 운영 로그 (6단계)

질문마다 두 곳에 남긴다. 응답 머리글 `X-Request-ID`가 둘을 잇는다.

| | 감사 기록 (`audit_log` 테이블) | 운영 로그 (표준 출력, JSON 한 줄) |
|---|---|---|
| 목적 | 누가, 무엇을, 어떤 권한으로 물었고 어떤 문서로 답했는지 (보안 조사) | 응답 시간, 오류, 비용 감시 (로그 수집 시스템으로) |
| 내용 | 사용자와 그 시점의 부서·역할·등급, 질문·답변 원문, LLM에 보낸 문서, 인용한 문서, 거절·검증 결과, 토큰·비용, 검색·첫 응답·전체 시간 | 같은 지표. **질문·답변 원문은 넣지 않는다** |
| 남는 경우 | 답변, 거절, LLM 실패, 사용자가 중간에 연결을 끊은 경우 | 위와 같고, 로그인 실패(401)도 남긴다 |

- 질문에는 개인정보가 섞일 수 있어 원문 저장은 설정으로 끌 수 있다 (`AUDIT_STORE_TEXT=false`면
  길이와 해시만). 보관 기간은 기본으로 두지 않는다(지우지 않음). 회사 정책에 맞춰 `AUDIT_RETENTION_DAYS`를
  정하면, 그보다 오래된 기록과 남은 기록이 가리키지 않는 조각 스냅샷을 하루 한 번 지운다:
  `uv run python -m rag_service.audit purge` (cron, 작업 스케줄러 등으로 실행).
- 사용자는 외래 키가 아니라 그 시점의 값을 복사한다. 퇴사나 부서 이동 뒤에도 "그때 어떤 권한으로
  무엇을 봤는지"가 남는다. 감사 테이블은 업무 테이블과 메타데이터를 나눠 두어, 나중에 별도 DB나
  읽기 전용 권한으로 옮기기 쉽다.
- 감사 기록 저장에 실패해도 이미 보낸 답변은 그대로 두고, 운영 로그에 `audit_write_failed`를 남긴다.
  로그 수집 시스템에서 이 이벤트에 경보를 걸어야 한다.

### LLM 사용 한도 (6단계, 마이그레이션 0008)

한 사용자의 반복 호출이나 스크립트 오용으로 비용이 쌓이지 않게, 질문 API가 LLM을 부르기 전에 확인한다
(`api/limits.py`). 넘으면 LLM을 부르지 않고 `429`와 `Retry-After` 머리글, 안내 문구를 돌려준다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `LLM_DAILY_REQUESTS_PER_USER` | 200 | 사용자별 하루 질문 수 |
| `LLM_DAILY_BUDGET_USD` | 20 | 회사 전체 하루 LLM 비용 (달러, Sonnet 기준 약 5천 질문) |
| `LLM_CONCURRENT_PER_USER` | 3 | 사용자별 동시에 처리 중인 질문 수 |
| `USAGE_UTC_OFFSET_HOURS` | 9 | "하루"의 기준 시간대 (9 = 한국 시간 0시에 초기화) |

- 값을 비우면 그 한도를 두지 않는다. 한도에 걸린 요청은 운영 로그에 `rate_limited`(이유, 사용자)로 남는다.
- 하루 질문 수와 비용은 감사 기록(`audit_log`)으로 센다. 서버를 여러 대 띄워도, 재시작해도 값이 같다.
  앱 계정은 감사 기록을 읽을 수 없으므로(질문 원문 보호), 두 숫자만 돌려주는 DB 함수
  `llm_usage_since`(`SECURITY DEFINER`)를 만들고 실행 권한만 준다.
- 동시 요청 수는 서버 프로세스마다 메모리로 센다. 끝났다는 신호를 받지 못한 자리는 10분 뒤 비운다.

**한계**
- 감사 기록은 답이 끝나야 남으므로, 동시에 몰린 질문은 하루 한도를 동시 요청 수만큼 넘길 수 있다.
- 동시 요청 수는 프로세스별이라 워커를 N개 띄우면 사용자당 최대 N배가 된다.
- 비용은 요금표(`answer/llm.py`의 `MODEL_PRICES`)에 있는 모델만 더한다. 대체 모델이 요금표에 없으면 0으로 센다.

### 인덱스 수명 관리 (스키마, 마이그레이션 0005)

RAG 구현 감사(2026-11-11)에서 나온 출처·버전 메타데이터, 원문과 인덱스 동기화 문제에 대한 대응이다.
수집할 때 아래 값을 함께 남긴다.

| 테이블 | 컬럼 | 뜻 |
|---|---|---|
| `documents` | `content_sha256` | 원문 파일 바이트의 해시. 원문이 바뀌었는지 판단하는 기준 |
| | `source_mtime` | 원문 파일 수정 시각 (참고용. git checkout 등으로도 바뀌므로 판단에는 쓰지 않는다) |
| | `embedding_model` | 이 문서의 조각을 임베딩한 모델 이름. 다른 모델의 벡터가 섞이는 것을 막는 데 쓴다 |
| | `effective_from`, `effective_to` | 시행일과 마지막 유효일(그날까지 포함). `acl.yaml`에서 읽고, 근거가 있는 날짜만 적는다 |
| `chunks` | `chunk_key` | "어느 조항인가": `{원문 경로}#{제목 경로}#{같은 제목 경로 안의 순번}`. 문서 안에서 유일 |
| | `content_sha256` | "정확히 어떤 문장인가": 조각 본문(제목 경로 포함)의 해시 |
| `chunk_snapshots` | `content_sha256`, `content` | 감사 기록이 가리키는 조각 본문. 내용 해시당 한 번만 저장한다 |

- `chunks.id`는 내부 키로만 쓴다. 재수집하면 바뀌므로 인용·감사·재현에는 `chunk_key`와 `content_sha256`을 쓴다.
- 0005 이전에 수집한 행은 새 컬럼이 비어 있다. 제목 경로가 DB에 없어 기존 행에서 키를 계산할 수 없으므로
  백필하지 않고, 한 번 재수집해서 채운다.
- 시행일은 추정하지 않는다. 지금 샘플에는 본문에 날짜가 있는 2개(16번 `effective_to: 2025-12-31`,
  17번 `2023-07-01 ~ 2023-12-31`)만 있고, 나머지는 "시행일 미상"이다. 날짜로 판을 고르는 검색은 아직 없다.
- 요청 형식에는 `PROMPT_TEMPLATE_VERSION`(`answer/prompt.py`)을 붙인다. 요청 문자열이 바뀌면 버전을 올려야
  하고, `tests/answer/test_prompt_version.py`가 해시로 이를 강제한다.

**한계**
- `chunk_key`에 원문 경로가 들어가므로 **파일 이름을 바꾸면 그 문서의 모든 키가 바뀐다.**
- 같은 제목 경로 안에서 앞쪽 조각이 나뉘거나 합쳐지면 뒤쪽 조각의 순번이 밀린다. 다른 섹션의 키는 그대로다.

### 증분 수집과 신선도 점검 (마이그레이션 0006)

수집은 바뀐 것만 처리한다 (`ingest/pipeline.py`). 원문 폴더를 정해진 시각에 다시 수집하는
방식(cron, 작업 스케줄러)을 전제로 한다.

```
uv run python -m rag_service.ingest samples            # 증분 수집
uv run python -m rag_service.ingest samples --dry-run  # 할 일만 출력 (모델을 읽지 않고 DB도 안 바꿈)
uv run python -m rag_service.ingest samples --prune    # 목록에서 빠진 이 폴더의 문서도 지운다
uv run python -m rag_service.ingest samples --force    # 전부 다시 청킹 (청킹 방식을 바꿨을 때)
uv run python -m rag_service.ingest check samples      # 원문과 인덱스 비교 (읽기 전용, 문제 있으면 종료 코드 1)
```

| 경우 | 처리 |
|---|---|
| 원문 해시와 임베딩 모델이 DB와 같음 | 건너뜀 |
| 원문이 바뀜 | 그 문서만 다시 청킹한다. 본문 해시가 같은 조각은 기존 벡터를 다시 써서 바뀐 조각만 임베딩한다 |
| 원문은 같고 `acl.yaml`의 권한·제목·상태·시행일만 바뀜 | 재임베딩 없이 값만 고친다 (조각에 복사한 권한 포함) |
| 임베딩 모델 이름이 바뀜 | 이 폴더 문서는 모두 다시 임베딩하고, 목록 밖 문서(다른 폴더 등)도 DB에 저장된 조각 본문으로 다시 임베딩한다. 한 DB에 두 모델의 벡터가 섞이지 않는다 |
| 목록(`acl.yaml`)에서 빠짐 | 기본은 지우지 않고 경고만 출력한다. `--prune`이면 **이번에 넘긴 폴더에서 수집한 문서만** 지운다 |

- 실행이 끝나면 추가·변경·메타데이터 갱신·건너뜀·삭제 개수와 걸린 시간을 출력한다. 전체가 한
  트랜잭션이라 중간에 실패하면 아무것도 바뀌지 않는다.
- `documents.corpus_root`(수집한 폴더의 절대 경로)로 폴더를 구분한다. 폴더를 옮겨서 수집하면 같은
  파일 이름의 문서를 새 폴더 것으로 바꿔 적는다 (재임베딩 없음). 0006 이전 행처럼 폴더를 모르는 문서는
  `--prune`으로 지우지 않는다.
- `check`가 오류로 보는 것: 원문 해시 불일치, 수집 안 된 원문, 원문 목록에서 빠진 DB 문서, `acl.yaml`과
  다른 권한·메타데이터, 기대한 모델과 다른 임베딩(DB 전체), 시행일과 `status`의 모순(`current`인데 마지막
  유효일이 지났거나 시행 전, `superseded`인데 아직 유효 기간). 시행일 미상은 경고만 한다. 기준일은
  `--today`, 모델은 `--embedding-model`로 바꿀 수 있다.
- CI는 품질 게이트가 평가 DB(`rag_eval`)에 수집한 뒤 `check samples`를 돌린다.
- `/health`는 `index`에 문서 수, 마지막 수집 시각(`last_synced_at`), 불일치 개수(`mismatches`:
  원문 수정 시각이 다름, 원문 없음, 수집 안 된 새 파일, 모델 불일치)를 보여 준다. 원문을 읽지 않고
  수정 시각만 보는 대략적인 값이므로, 정확한 판단은 `check`로 한다. 인덱스에 문제가 있어도 `status`는
  `ok`다.

**한계**
- 청킹 방식(`max_chars`, 파서)만 바뀌고 원문이 그대로면 알아채지 못한다. 그때는 `--force`를 쓴다
  (본문이 같은 조각은 벡터를 다시 쓰므로 비용은 바뀐 조각만큼이다).
- 사용자(`users`)는 지금도 마지막에 수집한 폴더의 `org.yaml`과 같게 맞춘다. 여러 폴더를 한 DB에
  수집하려면 조직 정보를 한 곳에 두어야 한다.

### 감사 재현 (마이그레이션 0007)

감사 기록에 LLM 요청을 다시 만들 수 있는 요소만 남긴다 (요청 본문 전체는 저장하지 않는다).

| 컬럼 | 내용 |
|---|---|
| `prompt_template_version` | 요청 형식 버전 (`answer/prompt.py`의 `PROMPT_TEMPLATE_VERSION`) |
| `model_params` | 요청한 모델과 파라미터 (`max_tokens`, `effort`, 대체 모델 설정) |
| `context_chunks` | 요청에 넣은 순서대로 `chunk_key`, `content_sha256`, 파일, 제목, 섹션, 페이지 |
| `request_sha256` | 실제로 보낸 요청(파라미터 + 시스템 프롬프트 + 사용자 메시지)의 해시 |

- 요청에 넣은 조각 본문은 `chunk_snapshots`에 내용 해시당 한 번만 저장한다 (감사 기록과 한 트랜잭션).
  원문이 바뀌어 재수집해도 "그때 LLM이 본 본문"이 남는다. 질문 원문 저장을 꺼도 스냅샷은 남긴다
  (사용자 입력이 아니라 문서 본문이므로).
- 점수 관문에서 거절해 LLM을 부르지 않은 기록은 재현 정보가 비어 있다.
- 개발 중에는 `LOG_PROMPTS=true`(+`LOG_LEVEL=DEBUG`)로 요청 원문을 로그로 볼 수 있다.
  운영(`AUTH_MODE=oidc`)에서는 켤 수 없고, 운영 로그에는 계속 원문을 넣지 않는다.

```
uv run python scripts/replay.py 42                      # 요청을 다시 만들어 당시 해시와 비교
uv run python scripts/replay.py 42 --question "..."     # 질문 원문을 저장하지 않은 기록 (해시만 비교)
uv run python scripts/replay.py 42 --call               # 같은 요청을 LLM에 다시 보냄 (API 비용 발생)
```

- 종료 코드: 0 해시 일치, 1 불일치, 2 재현할 수 없음 (기록 없음, 재현 정보 없음, 템플릿 버전이 다름,
  스냅샷이 지워짐, 질문 원문 없음 등 이유를 출력한다).
- `--call`은 기본으로 하지 않는다. 지금 설정한 LLM의 파라미터가 당시와 다르면 호출하지 않는다.
- 감사 테이블을 읽으므로 감사자 계정(`rag_auditor`)으로 실행한다.
- 한계: 템플릿 버전이 다르면 지금 코드로는 재현하지 않는다 (그 버전의 코드로 실행). LLM은 같은 요청에도
  답이 달라질 수 있어, `--call`의 답이 당시 답과 같다는 보장은 없다. 재현을 보장하는 것은 "요청"이다.

### 답변 LLM 선택 (6단계-4)

기본은 Claude API다. 문서 조각을 회사 밖으로 보낼 수 없는 회사는 사내 GPU 서버의 모델을 쓴다
(`answer/openai_compat.py`). vLLM, Ollama, LM Studio처럼 OpenAI 호환 API(`/v1/chat/completions`)를 내는
서버면 된다. 검색, 권한, 거절 판정, 인용 검증, 감사 기록은 LLM과 상관없이 같다.

```
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=http://gpu-server:8000/v1     # deploy/compose.yaml의 ollama: http://ollama:11434/v1
LLM_MODEL=gemma3:12b                       # 그 서버의 모델 이름
LLM_API_KEY=                               # 서버가 키를 요구할 때만
```

- temperature 0으로 보낸다. 사고 과정을 `<think>...</think>`로 먼저 쓰는 모델은 그 부분을 떼고 답만 쓴다
  (스트리밍 중에도 조각 경계와 상관없이).
- 비용은 0으로 기록한다(요금표에 없는 모델). 하루 예산 한도는 사실상 적용되지 않고, 질문 수·동시 요청 한도는 그대로다.
- 감사 재현(`scripts/replay.py`)은 기록된 제공자·주소·모델로 같은 LLM을 다시 만든다.
- 품질 비교: `uv run python scripts/compare_llm.py --base-url ... --model ...` (같은 검색 결과에 Claude는 평가 캐시,
  비교 모델은 실제 호출).

**측정 (2026-11-11, 골든 95문항, 검색 결과 동일)**: gemma3:12b를 Ollama 0.40.11(Docker, RTX 5070 Ti 16GB)로 실행

| 모델 | 거절해야 할 때 거절 | 잘못 거절 | 정답 위치 인용 | 인용 정밀도 | 인용 검증 통과 | 문항당 시간 | 문항당 비용 |
|---|---|---|---|---|---|---|---|
| claude-sonnet-5-5 | 1.000 | 0.000 | 1.000 | 0.902 | 0.973 | (API) | $0.0038 |
| gemma3:12b | 0.900 | 0.013 | 1.000 | 0.993 | 0.987 | 6.5초 | 0 (GPU 운영비 별도) |

실패한 문항을 원문과 대조했다.
- **u006 (오답)**: "일본 법인 설립 총비용"을 물었는데, 회의록의 "시장 조사 예산 2억 원"을 총비용으로 답했다. 인용한 조각에
  "2억 원"과 "2026년 예비비"가 그대로 있어서 **인용 검증도 통과했다.** 인용 검증은 숫자와 표현이 근거에 있는지를 볼 뿐,
  답이 질문에 맞는 뜻인지는 보지 못한다는 한계가 드러났다.
- **p001 (채점상 실패, 유출 아님)**: 볼 수 없는 인사 대외비 대신 볼 수 있는 취업규칙의 "세부 기준은 인사팀이 별도로 정한다"로
  답했다. 권한 밖 문서는 요청에 들어가지 않았다.
- **v005 (잘못 거절)**: "점심값"을 근거의 "식대"와 연결하지 못했다.

결론: 인용 형식은 잘 지키지만, 답이 없는 질문을 답이 있는 것처럼 읽는 경우가 Claude보다 많다. 사내 모델을 쓰려면 회사 문서로
같은 비교를 먼저 돌려 보고 정한다. 기본값은 Claude로 둔다.

**운영 메모**
- Ollama의 기본 문맥 길이(4096 토큰)를 넘으면 앞부분이 오류 없이 잘린다. compose 예시는 `OLLAMA_CONTEXT_LENGTH=8192`
  (샘플 문서의 요청은 약 1천 토큰).
- 측정 중 Ollama 0.40.11의 내부 서버가 응답 직후 프롬프트 캐시를 저장하다 가끔 죽었다(gemma3, 95문항 중 6번, 곧바로 복구).
  앱은 이때 `error` 이벤트("답변을 만들지 못했습니다")를 보내고 감사 기록에 남긴다. 자동 재시도는 하지 않는다
  (이미 일부를 보낸 스트림은 다시 보낼 수 없다). 동시 사용자가 많은 운영에는 vLLM 같은 서버를 권한다.
- compose 예시에 처음 고정했던 Ollama 0.6.8은 현재 모델 저장소에서 gemma3를 받지 못했다(버전이 낮다는 412 오류).

### 설치형 배포 (6단계)

회사 서버에 Docker Compose로 설치한다. **`cd deploy && docker compose up -d` 한 줄**이면 샘플 문서와 데모 로그인까지
준비된다(설정 파일 없이). 절차, 정기 작업, 백업·복구, 폐쇄망 설치는 [deploy/README.md](deploy/README.md).

| 파일 | 내용 |
|---|---|
| `Dockerfile` | 앱 이미지(약 2.5GB, CPU용 PyTorch). 모델 파일은 넣지 않고 `/models` 볼륨에서 읽는다 |
| `.github/workflows/release.yml` | 버전 태그(`v0.1.0`)를 올리면 품질 게이트 → 이미지 빌드 → 실행 점검 → `ghcr.io/jc032896/rag-service:0.1.0` 배포 |
| `deploy/compose.yaml` | `setup`(비밀번호·모델) → `db`(포트 비공개) → `migrate`(스키마, 로그인 계정) → `sync`(문서 증분 수집), `app`(127.0.0.1만) |
| `deploy/compose.override.yaml` | 데모 로그인(Keycloak)과 앱 연결. 자동으로 함께 읽히고, 운영에서는 지운다 |
| `deploy/.env.example` | 선택 설정(API 키, 회사 로그인, 문서 폴더, 한도). 비밀번호는 비워 두면 자동 생성 |
| `deploy/keycloak/hanbit-realm.json` | 데모 로그인: `samples/org.yaml`의 직원 6명과 이 앱(토큰 대상 `rag-service`) |

- **미리 만든 이미지**: compose는 코드 버전(`pyproject.toml`)과 같은 태그의 이미지를 받고(`pull_policy: missing`),
  받을 수 없을 때만 직접 빌드한다. 그래서 설치하는 서버는 빌드 도구와 5분의 빌드가 필요 없고, 받은 코드와 이미지의
  버전이 어긋나지 않는다. release는 태그가 `pyproject.toml`의 버전과 다르면 멈추고, 품질 게이트를 통과한 커밋만
  올린다. 이미지 안에서 비 root 사용자(10001)와 앱 import를 확인한 뒤에 올린다.
- **첫 실행 자동 준비**: `setup`(`python -m rag_service.deploy prepare`)이 시작할 때마다 한 번 돈다. 비밀번호 파일이
  없으면 무작위로 만들고(출력하지 않음), 모델은 없는 파일만 받는다. 비밀번호는 비밀 볼륨 세 개(소유자, 앱·감사,
  Keycloak)에 나눠 담아 필요한 서비스에만 붙이고, 서비스는 `*_PASSWORD_FILE`로 읽는다. 앱 컨테이너는 소유자
  비밀번호를 볼 수 없다. root로 도는 것은 `setup` 하나뿐이다.
- **모델 준비**: 앱은 `HF_HUB_OFFLINE=1`로 모델 볼륨만 읽는다. 폐쇄망은 받아 둔 모델 볼륨을 옮기고
  `OFFLINE_INSTALL=1`. 서버가 시작할 때 미리 읽어서(`PRELOAD_MODELS=true`) 첫 사용자가 기다리지 않는다.
  읽는 동안 `/ask`는 503(`Retry-After: 30`)이다.
- **상태 확인**: `/health`는 DB, 모델(`lazy|loading|ready|error`), 인덱스 신선도 요약(항상 200).
  `/ready`는 질문을 받을 수 있을 때만 200이라 컨테이너 상태 검사와 부하 분산기에 쓴다.
- **계정**: `migrate`가 `python -m rag_service.deploy create-db-users`로 앱 계정(`rag_app` 역할)과 감사 담당
  계정(`rag_auditor` 역할)을 만든다. 수집은 앱 계정, 보관 기간 삭제는 소유자 계정으로 실행한다.
- **검증(2026-11-11, 이 PC)**: 설정 파일 없이 `docker compose up -d` 한 번 → 비밀번호 4개 생성 → 모델 확인 →
  마이그레이션·계정 생성 → 샘플 22개 수집 → `/ready` 200 → 데모 Keycloak 토큰(kim)으로 `/ask` 인증 통과(API 키가
  없어 503에서 멈춤). 다시 실행하면 비밀번호를 그대로 둔다. 컨테이너마다 보이는 비밀 볼륨이 정해진 것뿐임을 확인.
  이전 검증: 위조 토큰 401, 실제 DB에서 앱 계정은 `audit_log`를, 감사 계정은 `documents`를 읽을 수 없음.
- **설정 빈 값**: compose는 비운 변수를 빈 문자열로 넘기므로, 빈 값은 "설정 안 함"으로 읽는다
  (예: `LLM_DAILY_BUDGET_USD=`이면 예산 한도 없음).
- **한계**: 완전 폐쇄망은 답변 LLM을 사내 모델로 바꿔야 한다(위 "답변 LLM 선택"). Keycloak 예시는 데모 설정
  (http, 고정 비밀번호, password grant)이고, Kubernetes(Helm)는 제공하지 않는다(무엇을 바꾸면 되는지만 정리).

### 관리 API (관리 화면 B-1)

관리 화면(React, 다음 단계)이 부르는 API다 (`api/admin.py`). 사용자 확인은 질문 API와 같고, **관리 역할은 회사
로그인 시스템 토큰의 그룹 값으로 정한다** (`api/roles.py`). 문서 열람 권한(부서·역할·등급)은 지금처럼 DB
`users`에서 읽으므로, 그룹은 관리 화면에서 무엇을 할 수 있는지에만 쓰인다.

| 역할 | 그룹 (기본값, 설정으로 변경) | 할 수 있는 일 |
|---|---|---|
| 중앙 관리자 | `ADMIN_GROUP=rag-admin` | 설치 상태, 사용자 목록, 전체 문서와 올린 문서의 권한 |
| 부서 문서 담당 | `DOC_MANAGER_GROUP=rag-doc-manager` | 설치 상태, 자기 부서 문서 올리기와 권한 지정 |
| 감사 담당 | `AUDITOR_GROUP=rag-auditor` | 감사 기록 목록과 한 건(질문·답변 원문, 재현 정보) |

| API | 역할 | 내용 |
|---|---|---|
| `GET /admin/api/me` | 로그인한 누구나 | 이름, 부서, 관리 역할 목록. 역할이 없어도 200 (화면이 "권한 없음"을 보여 준다) |
| `GET /admin/api/status` | 관리 역할 누구나 | DB, 모델, 인덱스 신선도, 답변 LLM 설정 여부, 감사 DB 연결, 사용 한도 |
| `GET /admin/api/users` | 중앙 관리자 | `org.yaml`에서 수집한 사용자와 권한 속성 (보기만) |
| `GET /admin/api/audit` | 감사 담당 | 최근 기록부터. `login`, `outcome`, `since`(포함), `until`(제외), `before_id`로 다음 페이지 |
| `GET /admin/api/audit/{id}` | 감사 담당 | 답변 원문, 근거 조각 목록, 요청 해시 (`scripts/replay.py`로 재현) |

- **역할은 서로 포함하지 않는다.** 중앙 관리자도 감사 담당 그룹에 없으면 감사 기록을 볼 수 없다(403). 운영 관리와
  감사 조사를 나누려는 것이다 (PRODUCT.md "역할을 섞지 않는다"). 거절은 운영 로그 `admin_forbidden`에 남는다.
- **감사 기록은 감사 담당 DB 계정으로 읽는다.** 앱 계정(`rag_app`)은 감사 기록을 읽을 수 없으므로 앱이 감사 담당
  계정(`AUDIT_DB_USER`, `rag_auditor` 역할)으로 따로 연결한다. 감사 기록을 본 사실(누가, 어떤 조건으로, 몇 건)은
  운영 로그 `admin_audit_viewed`에 남기고 질문 원문은 넣지 않는다.
- **트레이드오프**: 이 연결 때문에 앱 프로세스가 감사 담당 비밀번호를 갖는다. 앱이 뚫리면 감사 기록도 읽힐 수 있다
  ("배포: DB 계정 분리"의 보호가 약해진다). 이를 허용하지 않는 회사는 `ADMIN_AUDIT_VIEW=false`로 끄고, 감사 조사는
  감사 담당 계정으로 별도 도구(`scripts/replay.py`, DB 클라이언트)를 쓴다. 이때 감사 API는 503이다.
- 그룹 값의 이름은 `OIDC_GROUPS_CLAIM`(기본 `groups`)이다. Entra ID는 그룹 이름 대신 그룹 객체 ID를 보내므로
  `ADMIN_GROUP` 등에 그 ID를 넣는다. Keycloak은 그룹 매퍼의 "Full group path"를 끄거나 `/rag-admin`처럼 경로로 적는다.
- 개발 모드(`AUTH_MODE=dev_header`)는 `X-User-Groups: rag-admin,rag-auditor` 헤더를 그대로 믿는다 (데모 전용).
- 데모 로그인(`deploy/compose.override.yaml`)에는 han(중앙 관리자), lee(개발팀 문서 담당), park(감사 담당)이 들어 있다.
- 모델을 읽지 않으므로 서버가 모델을 읽는 중에도 관리 API는 응답한다.

### 문서 올리기와 권한 지정 (관리 화면 B-2, 마이그레이션 0009)

관리 화면에서 문서를 올리고 볼 수 있는 사람을 정한다 (`api/admin_documents.py`, `ingest/uploads.py`).
문서 폴더(`acl.yaml`)로 수집하는 방식은 그대로 두고, 출처를 나눠 서로 덮어쓰지 않게 했다.

| | 폴더 문서 (`origin=folder`) | 올린 문서 (`origin=upload`) |
|---|---|---|
| 권한의 원본 | 문서 폴더의 `acl.yaml` | DB (`document_acl`) |
| 관리 화면 | 보기만 (바꾸려 하면 409) | 올리기, 파일 교체, 권한 변경, 삭제 |
| 원문 위치 | `CORPUS_DIR/docs/<파일>` | `UPLOAD_DIR/docs/upload/<파일>` (`uploads` 볼륨) |
| `source_path` | `<파일>` | `upload/<파일>` (폴더 문서와 겹치지 않는다) |
| 폴더 수집 `--prune` | 목록에서 빠지면 지운다 | 건드리지 않는다 (`corpus_root`가 다르다) |

| API | 역할 | 내용 |
|---|---|---|
| `GET /admin/api/documents` | 중앙 관리자: 전체 / 문서 담당: 자기 부서 올린 문서 | 권한, 조각 수, 볼 수 있는 사용자 수, 바꿀 수 있는지 |
| `GET /admin/api/org` | 둘 다 | 고를 수 있는 부서·역할 |
| `POST /admin/api/documents/access-preview` | 둘 다 | **저장 전에** 이 권한으로 볼 수 있게 되는 사용자 |
| `POST /admin/api/documents` (multipart) | 둘 다 | 파일, 제목, 등급, 부서, 역할. 관리 부서는 문서 담당이면 자기 부서 |
| `PUT /admin/api/documents/{id}/access` | 둘 다 | 제목, 등급, 부서, 역할, 상태 (재임베딩 없음) |
| `PUT /admin/api/documents/{id}/file` | 둘 다 | 새 판으로 교체. 권한은 그대로, 본문이 같은 조각은 벡터 재사용 |
| `DELETE /admin/api/documents/{id}` | 둘 다 | 문서, 조각, 원문 파일 삭제 (이력은 남는다) |
| `GET /admin/api/documents/{id}/changes` | 둘 다 | 올리기·교체·권한 변경·삭제 이력 (누가, 언제, 전후 값) |

- **범위**: 부서 문서 담당은 자기 부서가 관리하는 올린 문서만 본다. 다른 부서 문서는 제목도 드러내지 않도록 404다.
  열람 권한은 다른 부서에도 줄 수 있다 (문서를 관리하는 부서와 볼 수 있는 부서는 다르다).
- **권한이 먼저다**: 부서·역할이 하나도 없는 권한과 없는 부서·역할은 거부한다(422). 화면은 저장 전에
  `access-preview`로 볼 수 있게 되는 사람을 보여 준다. 규칙은 검색의 권한 필터와 같다.
- **바로 반영**: 권한을 바꾸면 `document_acl`과 조각의 권한 사본을 함께 고친다. 재임베딩하지 않으므로 바로
  다음 질문부터 적용된다.
- **이력**: `document_changes`는 앱 계정이 넣고 읽기만 하고 고치거나 지울 수 없다(DB 권한). 감사 담당 계정도
  읽는다. 파일을 바꾸면 문서 id가 바뀌므로 이력은 `source_path`로 찾는다.
- **파일 처리**: 임시 폴더에 받아 읽어 보고(깨진 PDF, 본문 없는 스캔 PDF는 422) 수집한 뒤, DB 커밋이 끝나면
  제자리로 옮긴다. 커밋이 실패하면 임시 파일만 지우고, 기존 원문은 커밋 전까지 건드리지 않는다.
  허용 형식은 PDF·DOCX·MD, 크기는 `UPLOAD_MAX_MB`(기본 30MB, 넘으면 413), 파일 이름의 경로·제어 문자는 거부한다.
- **수집은 요청 안에서 한다**: 임베딩 모델로 바로 처리한다 (CPU, 2조각 문서 약 3~4초, 서버 시작 후 첫 요청은
  더 걸린다). 모델을 읽는 중이면 503이다. 큰 문서를 많이 올리는 환경은 작업 큐로 옮긴다 (로드맵 7단계).
- **검증(2026-11-12, 이 PC)**: 데모 Keycloak 토큰으로 lee(개발팀 문서 담당)가 올리기 → 같은 이름 409 →
  권한 미리 보기 → 인사팀까지 넓히기(볼 수 있는 사람 2→3명) → 파일 교체 → 삭제, han(중앙 관리자)은 폴더 문서 수정 409,
  kim(역할 없음)은 403. 이어서 폴더 수집 `--prune`을 돌려도 올린 문서는 남고 `/health` 불일치 0.

### 관리 화면 (web/admin, B-3)

React + TypeScript로 만든 관리 화면을 앱 이미지에 함께 넣어 `http://<서버>/admin`에서 제공한다
(`api/admin_ui.py`). 지금은 공통 틀(메뉴, 로그인)과 대시보드까지이고, 문서·사용자·감사 기록·설정 화면은 다음 단계다.

| 부분 | 내용 |
|---|---|
| 로그인 | 회사 로그인 시스템으로 이동하는 브라우저 로그인(authorization code + PKCE, `oidc-client-ts`). 토큰은 탭을 닫으면 사라지는 sessionStorage. 개발 모드(`AUTH_MODE=dev_header`)는 사람과 그룹을 직접 고른다 |
| 공개 설정 | `GET /admin/api/config`: 로그인 방식, 발급자와 클라이언트 id(`ADMIN_UI_CLIENT_ID`, 비우면 `OIDC_AUDIENCE`), 회사 이름·로고(`COMPANY_NAME`, `COMPANY_LOGO_URL`) |
| 메뉴 | 역할마다 할 수 있는 화면만 보인다. 관리 역할이 없으면 "관리 권한이 없습니다"와 요청할 그룹을 안내한다 |
| 대시보드 | 모든 역할이 같은 첫 화면: 송장 라벨 같은 상태 칸 4개(문서 색인, 검색 모델, 답변 LLM, 사용 한도), 최근 문서 전달(등기번호, 등급, 볼 수 있는 사람, 배송조회 단계), 확인할 일(막힌 것 먼저) |
| API 타입 | 서버 API 명세 사본 `web/admin/src/api/openapi.json`에서 `schema.d.ts`를 만든다(`npm run gen:api`). 사본이 실제 API와 다르면 pytest가, 타입이 사본과 다르면 게이트가 실패한다 |
| 글꼴 | Pretendard(본문), Barlow Condensed(숫자·등기번호)를 이미지에 넣어 폐쇄망에서도 같은 화면 |

- **시각 방향**: impeccable 스킬로 정했다. 질문(모든 역할이 같은 대시보드로 시작, 가끔 일이 생길 때 들어옴, 장식 과함·권한
  불안·빽빽함·흔한 템플릿은 실패)에 답한 뒤, 후보 7개 중 추첨으로 정해진 "등기·배송조회"를 선택했다: 문서는 허가된 사람에게만
  배달되고 모든 전달은 배송조회처럼 추적된다. 크라프트 상자색 메뉴 띠, 감열지 같은 흰 작업면, 보안 등급 네 색은 등급에만.
  방향 계약은 `.impeccable/surfaces/web-admin.md`.
- **접근성**: 본문 건너뛰기, 키보드 초점 표시, 표 머리글과 숨긴 캡션, 색만으로 구분하지 않는 상태(문구 함께), 대비 4.5:1 이상,
  움직임 줄이기 설정이면 배송조회 단계 움직임을 끈다. 좁은 화면은 메뉴가 위로 올라가고 표가 카드처럼 쌓인다.
- **검증(2026-11-12, 이 PC)**: 이미지 빌드 → 데모 Keycloak으로 브라우저 로그인(lee, park) → 대시보드 → 로그아웃까지 콘솔 오류 0.
  처음에는 Keycloak이 토큰 교환을 CORS로 막았다(데모 클라이언트의 웹 출처). 허용 출처를 명시해 고쳤고, 그런 실패 때 화면이
  원인과 다시 열기를 안내하게 했다.
- **데모 주소**: 브라우저와 앱 컨테이너가 같은 Keycloak 주소(`keycloak.localhost:8080`)를 써야 토큰의 발급자가 맞는다. 브라우저는
  `*.localhost`를 이 PC로 보내고, 컨테이너는 compose 네트워크 별칭으로 찾는다.
- **개발**: `cd web/admin && npm ci && npm run dev` (5173, 관리 API는 8000으로 넘긴다). 검사는 `npm run check`.

### 배포: DB 계정 분리

마이그레이션 0005가 로그인할 수 없는 역할 두 개를 만든다(이미 있으면 그대로 둔다).

| 역할 | 업무 테이블 (`documents`, `document_acl`, `chunks`, `users`) | 감사 테이블 (`audit_log`, `chunk_snapshots`) |
|---|---|---|
| `rag_app` | 읽기·쓰기 | **쓰기만** (읽기 불가) |
| `rag_auditor` | 접근 불가 | **읽기만** |

`chunk_snapshots`에는 기밀 문서의 본문 사본이 들어가므로, 앱 계정이 뚫려도 읽을 수 없게 한다.
단, 관리 화면의 감사 기록 보기를 켜면(기본) 앱 프로세스가 감사 담당 계정도 쓴다 ("관리 API"의 트레이드오프).
운영에서는 로그인 계정을 나눠 각 역할을 부여한다.

```sql
CREATE ROLE rag_service LOGIN PASSWORD '...' IN ROLE rag_app;      -- 앱 (.env의 POSTGRES_USER)
CREATE ROLE rag_audit_ops LOGIN PASSWORD '...' IN ROLE rag_auditor; -- 감사 담당자, 재현 스크립트
-- 마이그레이션·보관 기간 삭제(purge)는 테이블 소유자 계정으로 실행한다
```

**개발 환경의 한계**: 로컬과 CI는 `docker-compose.yml`의 `rag` 계정 하나(슈퍼유저)를 쓰므로 이 제한이
적용되지 않는다. 역할 권한은 테스트에서 `SET ROLE`로 따로 검증한다(`tests/db/test_migrations_lifecycle.py`).
역할을 만들려면 마이그레이션 계정에 `CREATEROLE` 권한이 필요하다. 없으면 DBA가 두 역할을 먼저 만든다.
앱은 스냅샷을 읽지 않고 쓰려고 충돌 대상 없는 `ON CONFLICT DO NOTHING`을 쓴다. 충돌 대상을 적으면
`SELECT` 권한이 필요하기 때문이다 (`tests/db/test_migrations_audit_replay.py`).
